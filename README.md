# SAP LeanIX skills

A plugin marketplace for AI coding agents (GitHub Copilot, Claude Code and anything that reads
`SKILL.md`) that work with the **SAP LeanIX** APIs. It ships one plugin, `leanix-api`, built from the
official SAP LeanIX documentation on the SAP Help Portal and the platform's public OpenAPI
specifications (captured 2026-10-26), with two emphases:

1. **Getting API access right**: technical users and API tokens, the OAuth2 client-credentials token
   exchange, Admin / Member / Viewer roles and per-type permissions, custom roles and virtual
   workspaces, least privilege per integration, and why a call returns 401, 403 or 429.
2. **Working with fact sheets**: the GraphQL API (facet filters, cursor pagination, inline
   fragments, JSON-Patch mutations for fields, lifecycle, tags, relations, external ids, archiving),
   the Integration API (LDIF, processors, synchronization runs, deletion scope), webhooks, metrics,
   Excel import/export, the MTM user-management API and the SAP LeanIX MCP server.

## Install

### GitHub CLI (any supported agent)

```bash
gh skill install jj1985/leanix-skills leanix-api            # GitHub Copilot, project scope
gh skill install jj1985/leanix-skills leanix-api --agent claude-code --scope user
```

### GitHub Copilot CLI

```bash
copilot plugin marketplace add jj1985/leanix-skills
copilot plugin install leanix-api@leanix
```

Or install the plugin directly from the repository subdirectory:

```bash
copilot plugin install jj1985/leanix-skills:plugins/leanix-api
```

To enable it declaratively for a repository, add it to `.github/copilot/settings.json`:

```json
{
  "extraKnownMarketplaces": { "leanix": { "source": "github", "repo": "jj1985/leanix-skills" } },
  "enabledPlugins": { "leanix-api@leanix": true }
}
```

### Claude Code

```text
/plugin marketplace add jj1985/leanix-skills
/plugin install leanix-api@leanix
```

### VS Code, Copilot coding agent, or any agent that reads `SKILL.md`

Copy `plugins/leanix-api/skills/leanix-api/` into `.github/skills/` (repository), or into
`~/.copilot/skills/`, `~/.claude/skills/` or `.agents/skills/`.

## Repository layout

```text
leanix-skills/
├── .github/plugin/marketplace.json        Copilot CLI marketplace manifest
├── .claude-plugin/marketplace.json        Claude Code mirror of the marketplace manifest
├── openapi/
│   ├── leanix.openapi.yaml                Curated OpenAPI 3.1 spec (canonical copy)
│   ├── build_spec.py                      Regenerates it from the official specs
│   └── official/                          SAP's public specs as served on 2026-10-26 (MTM, Pathfinder, Integration API, Webhooks, Metrics, Import/Export)
└── plugins/
    └── leanix-api/
        ├── plugin.json                    Agent Plugins 1.0 manifest (Copilot CLI, Codex and other clients)
        ├── .claude-plugin/plugin.json     Claude Code manifest
        └── skills/
            └── leanix-api/
                ├── SKILL.md
                ├── references/            auth-and-access, graphql-api, integration-api, other-apis, gotchas, OpenAPI copy, source-docs/
                ├── scripts/               leanix_api.py
                └── evals/                 three test cases (prompt, expected outcome, graders)
```

The plugin follows the [Agent Plugins 1.0](https://agent-plugins.org/) layout documented for
Copilot CLI: manifest at the plugin root, skills discovered from `skills/<name>/SKILL.md`. Claude
Code reads the `.claude-plugin/` mirrors. `gh skill` discovers `plugins/*/skills/*/SKILL.md`.

## Using the script

```bash
export LEANIX_HOST=https://acme.leanix.net        # or just the subdomain: acme, eu, us ...
export LEANIX_API_TOKEN=...                        # technical user token (Administration > Technical Users)
export LEANIX_WORKSPACE=acmeprod                   # optional guard: abort if the token belongs to another workspace

S=plugins/leanix-api/skills/leanix-api/scripts/leanix_api.py
python $S whoami                                   # workspace, role, user and expiry from the JWT
python $S probe                                    # read / write (validateOnly) / admin access, no changes
python $S model types ; python $S facets Application
python $S list Application --fields "id name ... on Application { lifecycle { asString } }" --csv apps.csv
python $S update <id> '[{"op":"replace","path":"/description","value":"..."}]' --validate-only
python $S sync ldif.json --test                    # Integration API dry run with status polling and warnings
python $S webhooks create-push my-hook https://hooks.example.com/lx --events FACT_SHEET_UPDATED
python $S users --csv users.csv ; python $S techusers list
python $S --help
```

Use one technical user per integration with the lowest role that works (Viewer for reads, Member
for fact sheet writes, Admin only for Integration API configuration, webhooks, user management and
meta model changes), set an expiry date, and rotate tokens with "Replace token". Archive instead
of delete; `processingMode: full` and `replace` patches on `/lifecycle` or `/tags` overwrite whole
collections.

## Scope and caveats

- Sources: the SAP LeanIX developer guide and administration documentation on
  `help.sap.com/docs/leanix/ea` (the former `docs.leanix.net` / `docs-eam.leanix.net` hosts redirect
  there), the public OpenAPI specifications served by `app.leanix.net`, the SAP LeanIX product
  update feed, and SAP sample code in `SAP-samples/leanix-scripts`. Community posts fill gaps and
  are marked *(unconfirmed)* in the references.
- Every workspace has its own meta model and GraphQL schema: type names, field keys, relation names
  and option keys differ (meta model v3 vs v4, custom fields). The references describe the default
  model; the in-app GraphiQL schema and `GET /models/dataModel` are the authority for a workspace.
- The curated OpenAPI file is a trimmed derivative of SAP's specs (which are copied verbatim under
  `openapi/official/`); GraphQL operations are documented in prose, not in the spec.
- Nothing here has been run against a live SAP LeanIX workspace. Issues and corrections are welcome.
